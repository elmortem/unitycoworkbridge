# Регрессии завершения восстановления PlayMode-сцен

## Наблюдения

В WaterWalk на 0.26.1 задача `Task_20260913_124657_522_2ea1ec1c` завершилась
успешно в 13:16:12 UTC (1 passed, Evidence valid). Следующая задача
`Task_20260913_124658_627_a1d368a4` стартовала лишь в 13:19:20 UTC.
При чтении её состояния HasResult был false; это уже другой прогон.
По одному ready/Playing:no нельзя заключать, что активен именно предыдущий тест.

В коде восстановления обнаружены и воспроизведены независимые дефекты:
вызов до результата, вмешательство в cleanup активного Test Framework,
повторный вход из editor callback, повторная загрузка сцены при ошибке финализации,
утрата владельца при отложенной финализации.

## Исправление 0.26.3

- Восстановление ждёт HasResult и завершения Test Framework.
- Вложенные вызовы защищены флагом с finally, отложенный callback снимается при входе.
- Фаза ScenesRestored сохраняется на диске до финализации. Повторная попытка
  завершает запись результата, не загружая сцены заново.
- Если финализация ещё не записала терминальный статус, владелец восстановления
  остаётся сохранённым. При отмене терминальную запись выполняет TestRunLifecycle.

## Регрессионные проверки

`AgentBridgeRecovery.Tests` компилирует настоящие PlayModeSceneRecovery.cs и
PlayModeSceneState.cs; внешние Unity callbacks, состояние Test Framework и сбой
финализатора задаются управляемыми заглушками. Проверка не дублирует алгоритм
восстановления. Запуск: `dotnet run --project AgentBridgeRecovery.Tests -c Release`.

Один и тот же набор запущен со старыми файлами из 1a778b4 и с исправленными:
старый код — FAIL 5/5, новый — PASS 5/5. Проверка включена в Release Contract.

Живое воспроизведение в Unity 2022.3.62f2:
`Task_20260913_162350_271_reentrant_recovery` — две загрузки через вложенный
sceneManagerSetupRestored, несмотря на отсутствие результата, состояние удалено.
После исправления `Task_20260913_162529_005_scene_recovery` и
`Task_20260913_163214_349_scene_recovery` подтвердили ожидание результата,
единственную загрузку при вложенном callback и безвредность позднего callback.

`scripts/verify-scene-recovery.ps1` дополнительно запускает два коротких успешных
PlayMode-теста и после каждого требует выполнения следующей C#-задачи при отсутствии
TestRunLifecycle, активного Test Framework и pending scene recovery. Одних зелёных
счётчиков NUnit недостаточно: stale_input считается отказом проверки.

Первые два живых PlayMode-прогона дали 1 passed, но stale_input, поэтому не зачтены
как успешная приёмка. В checkout одновременно шли изменения другого агента;
без пути изменённого входа авторство события не устанавливается.

Последний прогон живой проверки подтвердил продвижение очереди после обоих тестов:
`Task_20260913_133702_640_c2f887ec` → `Task_20260913_163706_266_recovery_follower_1`,
`Task_20260913_133708_475_bed74e4d` → `Task_20260913_163712_115_recovery_follower_2`.
Оба последователя выполнились без активного test lifecycle, Test Framework или
pending recovery. Тестовые результаты всё ещё stale_input, и скрипт корректно
завершился с ошибкой приёмки, несмотря на подтверждённое продвижение очереди.
Отдельный файловый наблюдатель во время `Task_20260913_133612_410_fbf04461` увидел
только создание/удаление `Assets/InitTestScene*.unity` и его meta. Причину учёта этих
событий слоем evidence в рамках исправления восстановления не меняли.

Повторная проверка отмены подтвердила EditMode timeout и timeout с recovery,
но PlayMode-сценарий пересёкся с другим прогоном и был остановлен CLI: canceled
вместо ожидаемого timeout. Полный прогон verify-test-cancellation не зачтён.

Обновление WaterWalk и исчезновение задержки в его конкретной среде нужно
подтвердить отдельно: эти регрессионные проверки не доказывают устранение всех
возможных причин задержки его очереди.
