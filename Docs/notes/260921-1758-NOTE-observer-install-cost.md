# Чего стоит установка наблюдателя за входами

Заметка к ТДД `260921-1758-TDD-shared_input_observer`. Числа сняты в хост-проекте
`AgentBridgeUnity` (Unity 2022.3.62f2, Windows) задачами `csharp` до и после изменения.

## Причина

Unity подставляет не Win32-наблюдатель, а `System.IO.DefaultWatcher` — опрашивающую реализацию Mono.
Проверено прямо в редакторе рефлексией по приватному полю `FileSystemWatcher.watcher`:

```
backend=System.IO.DefaultWatcher
```

Отсюда два свойства, которых нет у наблюдателя .NET на Windows:

- `EnableRaisingEvents = true` синхронно обходит всё дерево корня, чтобы снять исходный слепок.
  Цена линейна по числу файлов и целиком ложится на поток, который ставит наблюдатель.
- События приходят не из ядра, а из следующего круга опроса. Задержка доставки на большом дереве —
  секунды, а не миллисекунды.

## Фикстура

`Temp/AgentBridge/ObserverFixture` — 8000 мелких файлов в 80 папках, вне корней входов проекта.

## До изменения (пакет 0.31.1)

| Что | Значение |
|---|---|
| Установка наблюдателя на главном потоке, первый монитор | 735 мс |
| То же, второй монитор того же корня | 702 мс |
| Снос обоих наблюдателей | 76 мс |
| Установка на реальных корнях хост-проекта (3 корня, маленький проект) | 30 мс |
| Задержка первой доставки события | 137 мс |
| Задержка второй доставки на том же живом наблюдателе | 11 242 мс |

Второй монитор платит столько же, сколько первый: каждый обходит дерево сам.

Числа из DeadliftUnity (7231 файл входов), приведённые в ТДД: 410–502 мс на установку для `Assets`,
`coordinator_slow_stage Stage=update` 70 раз за 70 секунд прогона, 401–1010 мс.

## После изменения (пакет 0.32.0)

| Что | Значение |
|---|---|
| `OpenAsync` на холодном хабе, время главного потока до возврата `Task` | 0 мс |
| `OpenAsync` на холодном хабе, полное время (рабочий поток) | 581 мс |
| Синхронный конструктор на тёплом хабе | 0 мс |
| `OpenAsync` на тёплом хабе, время главного потока | 0 мс |
| Синхронный конструктор на доживающем наблюдателе после `Dispose` последнего окна | 0 мс |
| `OpenAsync` на реальных корнях хост-проекта, время главного потока | 3 мс |

`WatcherCount` в момент замера был равен 3 ещё до первого обращения задачи: ежесекундный
`CachedResultServer` держит `Assets`, `Packages` и `ProjectSettings` тёплыми, и всё, что открывает
окно над теми же корнями, не платит за установку вовсе.

## Побочное следствие: наблюдатель начал работать

Опрашивающий наблюдатель на дереве в 8000 файлов отдаёт событие за время порядка круга опроса —
здесь 11 секунд. До изменения `CachedResultServer` ставил свой наблюдатель и сносил его в пределах
одной секундной проверки, то есть наблюдатель не доживал до первого полного круга и не мог сообщить
ни о чём: условие `monitor.EventCount == 0` в `CanPublish` на большом проекте выполнялось само собой.
Общий наблюдатель живёт между проверками и продолжает опрашивать, так что проверка кеша впервые
получает настоящее второе свидетельство, а не пустой счётчик.

## Как перемерить

Задачи лежали в `Temp/AgentBridge/` хост-проекта и в репозиторий не входят: мерить нужно на том
проекте, где стоит вопрос, а фикстуру создавать вне корней входов. Замер главного потока — вокруг
вызова `ValidationInputMonitor.OpenAsync(...)` до `await`, а не вокруг всего `await`.
